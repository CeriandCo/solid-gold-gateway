# C-10 — admin sign-in link diagnosis

Date: 2026-10-02 (UTC). Target account: `hoangvh238.dev@gmail.com`.

## Verdict

The primary hypothesis is **not** the cause. `sendAdminSignInLink`
(`src/lib/admin.server.ts`) already passes `shouldCreateUser: false`, and the auth
server accepts the request. Public sign-up stays disabled and was not touched.

The request path is healthy end to end; what is missing is a **verified sending
domain**. The project has no email domain configured, so auth emails leave via the
default shared sender, which Gmail routinely filters or drops. Lovable's managed
delivery log has **no events at all** for this recipient, which is consistent with
the mail never passing through managed delivery.

## Checks

### 1. Raw result of the sign-in link request

`POST {SUPABASE_URL}/auth/v1/otp?redirect_to=https%3A%2F%2Fsolid-gold-gateway.lovable.app%2Fadmin`

| body | status | response |
| --- | --- | --- |
| `{"email":"hoangvh238.dev@gmail.com","create_user":false}` | `200` | `{}` |
| `{"email":"hoangvh238.dev@gmail.com","create_user":true}` | `429` | `{"code":429,"error_code":"over_email_send_rate_limit","msg":"For security purposes, you can only request this after 58 seconds."}` |

The 429 on the second call is the per-address 60-second cooldown that the *first*
call opened — i.e. the first call was accepted and an email was dispatched. No
`signup_disabled` / "Signups not allowed for otp" error was ever returned.

Auth server settings (`GET /auth/v1/settings`):
`{"external":{...,"email":true},"disable_signup":true,"mailer_autoconfirm":false,...}`

Four further requests, spaced 65 s apart, all returned `200 {}` — no hourly cap was
reached during testing.

### 2. Dispatch and sender

- `check_email_domain_status`: **no email domain configured**, setup `not_started`.
  Auth emails therefore go out through the default shared sender.
- `list_email_logs` for this recipient: **no delivery events** in the visible
  14-day window (history visible from 2026-09-08T17:55:44Z). Auth mail sent by the
  default sender does not appear in managed delivery logs, so this is not proof of
  a failed send, but it does mean there is **no deliverability signal at all** —
  no bounce, no complaint, no suppression to act on.
- `check_email_suppression`: **not suppressed** (global scope; no sender apex to
  check because no domain is verified).
- Rate limits actually observed: 60 s per address. No hourly ceiling was hit in
  six sends inside ~10 minutes, so rate limiting is not the blocker.

### 3. Redirect origin

Accepted. `GET /auth/v1/verify?...&redirect_to=https://solid-gold-gateway.lovable.app/admin`
returns `303` to `https://solid-gold-gateway.lovable.app/admin#error=...`, preserving
the path. A control with a non-allowlisted origin
(`https://not-allowed-example.com/admin`) falls back to the site URL
(`https://solid-gold-gateway.lovable.app/`), confirming the allowlist is enforced
and that our origin is on it.

### 4. Password sign-in path

Works. A throwaway account (`c10-probe-…@example.com`) was created with a password
generated at runtime, signed in successfully through the publishable client
(session issued), then deleted. The password was never printed and the real
account's password was neither read nor changed.

Account state for `hoangvh238.dev@gmail.com`: exists, email confirmed, created
2026-09-19T06:19:52Z, last sign-in 2026-09-22T17:53:12Z, not banned.

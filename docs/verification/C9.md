## 4. Consent record — design choice

Chose three columns on `gift_card_orders` rather than a separate `purchase_acknowledgements` table.

Reason: today the acknowledgement is one-to-one with an order, the order row is already created inside the same checkout call, and adding columns keeps the write in the existing single insert — no second write and therefore no chance of an order existing without its consent record. A separate table would only earn its keep with multiple acknowledgements per order or acknowledgements without an order, neither of which exists.

Live schema after migration `0023` (queried this run):

```
acknowledged_at   | timestamp with time zone | nullable YES
acknowledged_text | text                     | nullable YES
terms_version     | text                     | nullable YES
```

Nullable because rows written before this task have no consent record; every new order writes all three. Written server-side in `runGiftCardCheckout`:

```
terms_version:     ACKNOWLEDGEMENT_VERSION
acknowledged_text: acknowledgementRecordText("gift_card")   // rebuilt on the server, not trusted from the browser
acknowledged_at:   new Date().toISOString()
```

## 5. Server enforcement — raw evidence

Schema: `acknowledged: z.literal(true)` inside the existing `.strict()` checkout input. Anything other than literal `true` (missing, `false`, `"true"`) fails validation and returns the same generic shape used by every other refusal.

Live call with the acknowledgement stripped from the request in the browser (Playwright route interception rewriting the outgoing payload keys, i.e. exactly what a devtools user can do), raw response body from `/_serverFn/…createGiftCardCheckout`:

```
HTTP 200
{"t":10,"i":0,"p":{"k":["result","error","context"],"v":[{"t":10,"i":1,"p":{"k":["ok","code"],"v":[{"t":2,"s":3},{"t":1,"s":"invalid_request"}]},"o":0},{"t":2,"s":1},{"t":11,"i":2,"p":{"k":[],"v":[]},"o":0}]},"o":0}
```

Decoded: `{ ok: false, code: "invalid_request" }`. Server log for the same call:

```
[commerce-checkout] refused: S7_BAD_INPUT
```

Direct `curl` calls against the same endpoint, server log lines in order:

```
acknowledged missing → [commerce-checkout] refused: S7_BAD_INPUT
acknowledged false   → [commerce-checkout] refused: S7_BAD_INPUT
acknowledged true    → [commerce-checkout] refused: S7_ORIGIN originPresent=true allowedCount=4
```

The third line is the proof that the acknowledgement check is what stopped the first two: with it ticked the request passes input validation and is refused later, at the origin allowlist.

No order is written on rejection — asserted in `src/lib/commerce-checkout.server.test.ts` ("rejects a purchase without the acknowledgement and writes no order", covering missing / `false` / string `"true"`), and a second test ("records the acknowledgement version, text and time on the order") asserts the recorded version, exact text and timestamp on the accepted path. Both run against the throwaway database.

## 7. Reaching Stripe Checkout after ticking — what was and was not verified

Verified: after ticking, the click fires the real checkout call, the request carries `acknowledged` and `termsVersion`, and the server accepts the input (`S7_BAD_INPUT` is gone; the refusal moves to the next gate).

Not verified end-to-end to `checkout.stripe.com` from this sandbox, and I will not claim it. The reason is the operator-owned origin allowlist in `commerce_settings`:

```
["https://id-preview--dfb6b88e-1020-4c5e-920c-1659e913f2e8.lovable.app",
 "https://project--dfb6b88e-1020-4c5e-920c-1659e913f2e8-dev.lovable.app",
 "https://project--dfb6b88e-1020-4c5e-920c-1659e913f2e8.lovable.app",
 "https://solid-gold-gateway.lovable.app"]
```

`http://localhost:8080` is not on it, so every local checkout stops at `S7_ORIGIN` and the page shows "We couldn't start checkout. Please try again." Chromium refuses to spoof the `Origin` header, and a server-side spoof is rejected by the framework's cross-origin guard (`Forbidden`). Adding localhost would mean editing operator-owned `commerce_settings`, which the project rules forbid.

What this leaves: the Stripe session creation path itself is exercised in the test suite after the acknowledgement passes — "records the acknowledgement version, text and time on the order" reaches Stripe and fails only on the deliberately invalid test key (`S7_SESSION_CREATE type=StripeAuthenticationError status=401`), which proves the acknowledgement gate does not block the Stripe path. Confirming the final redirect to `checkout.stripe.com` requires running the ticked flow on an allowlisted origin, i.e. after the client publishes.

# S2 — Gift card Checkout bound to a Stripe Product catalog (sandbox-first)

No Stripe key or secret was requested, printed, logged or stored. Nothing was published.

## What changed

### 1. Database — `drizzle/migrations/0018_gift_card_denomination_stripe_prices.sql`

- `gift_card_denominations` gains nullable `stripe_price_id_test` and `stripe_price_id_live`.
- Partial unique indexes on each column (unique when not null).
- RLS untouched: still enabled with no policies, service-role grants only.
- New `public.gift_card_set_stripe_prices(text, jsonb)` — SECURITY DEFINER, writes the whole
  mapping for one mode in a single transaction (clears that mode first, then applies the map,
  raising on an unknown denomination or empty id).
  `REVOKE ALL ... FROM PUBLIC, anon, authenticated`; `GRANT EXECUTE ... TO service_role`.

### 2. `src/lib/commerce/stripe-catalog.server.ts` (new, server-only)

- `keyMode()` → `'test' | 'live' | 'unset'` from the `STRIPE_SECRET_KEY` prefix
  (`sk_test_`/`rk_test_` → test, `sk_live_`/`rk_live_` → live, anything else → unset).
  The key value is never returned, logged or included in any result.
- `lookupKeyFor(currency, amountCents)` → `sqoot_gift_card_${currency}_${amount_cents}`.
- `syncStripeCatalog(deps?)` — requires `commerce_settings.currency`; fetches
  `stripe.prices.list({ lookup_keys, expand: ['data.product'], active: true, limit: 100 })`
  and validates every price: exactly one price per lookup key, `unit_amount === amount_cents`,
  `currency` matches, `type === 'one_time'` and not recurring, `active`, `livemode` matches the
  key mode, product present, active, `metadata.purpose === 'sqoot_gift_card'`, and all prices on
  ONE product. Only when every denomination passes does it write, through
  `gift_card_set_stripe_prices` (one transaction). Otherwise it writes nothing and returns a
  structured `problems[]`. Either way it records a `commerce_alerts` row of kind `catalog_sync`
  (info on success, warning on refusal) containing only problem codes and lookup keys.
- `catalogStatus()` → `{ mode, currency, mapped, expected, ready, productId?, lastSync }`;
  reads the database only, makes no Stripe call.
- `priceIdForDenomination(id, mode)` helper.

### 3. Checkout

- `src/lib/commerce.functions.ts` — `getGiftCardOffering().available` now also requires
  `catalogStatus().ready`.
- `src/lib/commerce-checkout.server.ts` — the denomination read now also selects both price
  columns; the price id for the current mode is resolved, and a missing one returns the generic
  `unavailable` code with no detail and no order written.
- `src/lib/commerce/session-params.ts` — `line_items: [{ price: <mapped price id>, quantity: 1 }]`;
  `price_data` is gone, `currency` is set on the session. 3-D Secure `any`, `custom_fields`,
  `expires_at`, `client_reference_id`, metadata and the `gift-card-${attemptId}-${denom.id}`
  idempotency key are all unchanged.
- The webhook still checks `amount_total` and `currency` against the order
  (`src/lib/stripe-webhook.server.ts`) — unchanged.

### 4. Admin

- `src/lib/commerce-admin.functions.ts` (new): `getStripeCatalogStatus` and
  `runStripeCatalogSync`, both behind `requireSupabaseAuth` and an allowlist role check through
  the caller's own user-scoped session.
- `src/routes/admin.settings.tsx`: a "Stripe" card showing the mode badge
  (Sandbox / Live / Not configured), currency, `mapped x/y` with a ready flag, the product id, the
  last check result, the problem list after a refused check, and a "Verify catalog" button.
  No key or key fragment is displayed anywhere. Styling reuses existing admin classes only.

### 5. Tests

- `src/lib/commerce/stripe-catalog.test.ts` (new, fake Stripe client).
- `src/lib/commerce/session-params.test.ts` updated for the price-id line item.
- `src/lib/commerce-checkout.server.test.ts` maps placeholder sandbox price ids for its scenarios
  and adds the unmapped case.
- `src/lib/security/function-privileges.test.ts` needed no change: the new function is
  SECURITY DEFINER, revoked from anon/authenticated, granted to service_role, and therefore
  already satisfies the existing allowlist assertions.

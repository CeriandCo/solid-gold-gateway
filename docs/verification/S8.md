# S-8 — Tests can no longer touch operator data; catalog safety net

Date: 2026-09-21. No secret value is printed anywhere in this document.
`checkout_enabled` was not changed. Nothing was published.

## 1. Isolation: the commerce suites no longer use the live database

Snapshot-and-restore is gone as the primary protection. The commerce suites now
run against a throwaway Postgres + PostgREST pair created per test run.

- `scripts/test-db/up.sh` — initdb + Postgres on 54329 (run as an unprivileged
  user), loads a `pg_dump --schema-only` copy of the live `public` schema plus a
  `--data-only` copy of the two reference tables (`commerce_settings`,
  `gift_card_denominations`), then starts PostgREST on 54330 with
  `db-anon-role = service_role` so `supabaseAdmin` behaves as it does in
  production. Both live reads are read-only.
- `scripts/test-db/proxy.mjs` — presents PostgREST as a Supabase endpoint
  (`/rest/v1/*`), on 54331. `/auth/v1/*` returns 501 by design.
- `scripts/test-db/down.sh` — stops both processes and deletes the data
  directory. Run by the vitest global teardown.
- `src/test/global-setup.ts` — starts/stops the stack around the run.
- `src/test/setup-isolated.ts` — points `SUPABASE_URL` /
  `SUPABASE_SERVICE_ROLE_KEY` at the local stack in every worker, before any
  test module is imported, then asserts that it took effect.

Suites moved to the isolated database: `commerce-checkout.server`,
`stripe-catalog`, `settings-fixture`, `stripe-webhook.server`,
`stripe-webhook-refunds.server`, `gift-delivery.server`, plus every pure unit
suite. `gift_card_set_stripe_prices(mode, {})` in `stripe-catalog.test.ts` now
clears a local table only.

Two suites still need the real project and are separated out:

| Project | Files | Behaviour |
| --- | --- | --- |
| `isolated` (default) | everything else | local throwaway database |
| `live-readonly` (default) | `src/lib/security/function-privileges.test.ts` | live, but any privileged non-read request is blocked in-process |
| `live-write` (opt-in) | `admin-password.server.test.ts`, `security/rest-surface.test.ts` | only runs with `ALLOW_LIVE_DB_TESTS=1`; creates its own temporary auth users, never commerce rows |

## 2. Hard guard

`src/test/live-db-guard.ts`:

- `assertIsolatedDatabase()` throws unless `SUPABASE_URL` resolves to
  `127.0.0.1` / `localhost`. Runs in every isolated worker at setup time, so a
  misconfigured run dies before the first test.
- `assertLiveOptIn()` throws unless `ALLOW_LIVE_DB_TESTS=1`. The `live-write`
  project is also omitted from the config entirely without that variable.
- `enforceReadOnlyFetch()` rejects any privileged (service-role) request to the
  live project that is not a GET/HEAD or a read-only `rpc` POST. Deliberate
  anon-key write probes are left alone — proving RLS rejects them is the point
  of that suite.

Covered by `src/test/live-db-guard.test.ts` (4 tests).

## 3. Safety net

`src/lib/commerce/catalog-guard.server.ts`:

- `reassertCatalog()` — idempotent. Reads `catalogStatus()`; if ready it reports
  and stops. If not ready it re-runs `syncStripeCatalog()` (which still refuses
  to write unless every denomination validates), then writes a
  `commerce_alerts` row of kind `catalog_guard`: `warning` when repaired,
  `critical` when it could not be. Alerts are throttled to one per 30 minutes.
  **It never changes `checkout_enabled`.**
- `runScheduledCatalogCheck()` — the cheap variant used on a schedule: a single
  read of the stored mapping, no Stripe call while healthy, never throws.
- Scheduling reuses the existing pg_cron pattern: `runDeliveryTick()` (job
  `commerce-delivery-tick`, `*/5 * * * *`, the vault-secret + `net.http_post`
  pattern already in place) now runs the check first, before its own
  `delivery_enabled` early return. That gives detection well inside the 30
  minutes asked for, with no new secret plumbing. A dedicated pg_cron job was
  not added because creating the new vault entry it would need is not available
  to the agent.
- `src/routes/api/public/commerce-catalog-check.ts` — standalone endpoint for a
  manual or externally scheduled run, gated by the same `x-cron-secret` header
  with a constant-time comparison.
- `scripts/s8-catalog-guard.ts` — one-off manual run.

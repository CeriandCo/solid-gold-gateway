## B/C. newsletter_signups

| column | type | null | purpose | controlled by |
|---|---|---|---|---|
| id | uuid PK default gen_random_uuid() | no | identity, stable across re-consent | server |
| email | text | no | server-normalised address | client value, server-normalised |
| lists | text[] | no | MELT content preferences | client, allowlisted |
| consent_version | text | no | version of wording accepted | server |
| consent_text | text | no | exact wording snapshot | server |
| consented_at | timestamptz | no | when this consent snapshot was accepted | server |
| source | text | no | bounded signup context | client, length-capped |
| created_at | timestamptz default now() | no | record creation | database |
| updated_at | timestamptz default now() | no | last modification | database trigger |

Constraints, read back from the live database:

```
newsletter_signups_email_unique        UNIQUE (email)
newsletter_signups_email_len           CHECK length(email) BETWEEN 3 AND 254
newsletter_signups_email_normalised    CHECK email = lower(email) AND email = btrim(email)
newsletter_signups_lists_not_empty     CHECK cardinality(lists) >= 1
newsletter_signups_lists_allowed       CHECK lists <@ ARRAY['daily-note','weekly-brief']
newsletter_signups_consent_version_len CHECK length(btrim(consent_version)) BETWEEN 1 AND 80
newsletter_signups_consent_text_len    CHECK length(btrim(consent_text)) BETWEEN 1 AND 4000
newsletter_signups_source_len          CHECK length(btrim(source)) BETWEEN 1 AND 200
```

No second raw-email column. No Unicode folding in SQL.

## D. lists semantics

Audited browser values in `src/components/aurum-subscribe-section.tsx`: the checkbox ids are `daily-note`
and `weekly-brief`. Those exact strings are the allowlist. They are our content choices, not provider
audience or list identifiers, and no column or constraint name mentions a vendor.

The UI already refuses submission with nothing selected ("Choose at least one thing to receive."), so the
DB mirrors that invariant: at least one element, allowlisted values only. A single array column, not two
booleans — the form already models this as a multi-select set.

## E. Consent fields

Schema only. No seed rows, no placeholder consent text, no fabricated approved version — `SELECT count(*)
FROM newsletter_signups` returns 0. The non-empty/length CHECKs make an empty consent snapshot impossible
to store later. `consented_at` is `timestamptz`, set by the server at acceptance time.

## F. source

Single bounded `text` column, 1–200 characters. No UTM/gclid/referrer fields, no IP, no provider source id.
The form's wider attribution payload is deliberately not persisted in this phase.

## G. Timestamps

`created_at`/`updated_at` default to `now()`. `updated_at` is maintained by trigger
`newsletter_signups_updated_at` → `public.newsletter_signups_set_updated_at()`, mirroring
`aurum_posts_set_updated_at`. `consented_at` is never touched by the trigger; proven by test.

## H. Uniqueness / upsert readiness

`UNIQUE (email)` supports `ON CONFLICT (email) DO UPDATE`. Proven by test: lists, consent version,
consent text, consented_at and source all update while `id` and `created_at` stay identical.

## I/J/K. newsletter_attempts

`id bigserial PK`, `ip_hash text NOT NULL`, `created_at timestamptz NOT NULL DEFAULT now()`. No kind column
(only one newsletter operation exists). No raw IP, email, user agent, referrer or payload — proven by a test
asserting the column list is exactly `id,ip_hash,created_at`.

Index `newsletter_attempts_ip_created_idx (ip_hash, created_at)` — the same shape as
`checkout_attempts_ip_created_idx`, and the only index added.

Pepper: the future secret is `NEWSLETTER_HASH_PEPPER`, deliberately separate from `COMMERCE_HASH_PEPPER`.
It is **not** created in this phase and is not referenced in SQL; the database stores only the hash.

## L/M. Prune function and cron

`public.newsletter_prune_attempts()` — `LANGUAGE sql`, `SECURITY DEFINER`, `SET search_path TO 'public'`,
deletes `newsletter_attempts` older than 7 days. `REVOKE EXECUTE … FROM PUBLIC, anon, authenticated`;
`GRANT EXECUTE … TO service_role`. It never touches `newsletter_signups`.

The repository registers pg_cron jobs inside migrations, so the same was done. Read back from `cron.job`:

## N/O. RLS, grants, sequence

Read back from the live database:

```
newsletter_signups  relrowsecurity=true  policies=0
newsletter_attempts relrowsecurity=true  policies=0
has_sequence_privilege('service_role','newsletter_attempts_id_seq','USAGE') = true
```

`GRANT ALL … TO service_role` on both tables plus `GRANT USAGE, SELECT ON SEQUENCE … TO service_role`,
matching `aurum_admin_login_attempts`. No anon/authenticated policies of any kind were created. The platform
applies its own blanket table grants to `anon`/`authenticated` (identical to `checkout_attempts`), which is
exactly why RLS-with-no-policies is the control that matters — proven over real HTTP below.

## Q/R. Database tests

`src/lib/newsletter/newsletter-schema-db.test.ts` → **17 passed**, throwaway database only
(`assertIsolatedDatabase()` in force). Covers: valid row accepted; duplicate email rejected (23505);
over-length email rejected; non-normalised email rejected; empty list rejected; unsupported list value
rejected; both choices accepted; empty consent version rejected; empty consent text rejected; empty source
rejected; no provider/confirmation/sync columns; created_at and updated_at populated; updated_at moves on
update while created_at and consented_at do not; upsert re-consent keeps id and created_at; two concurrent
connections upserting the same email leave exactly one row; attempts accept a hash and stamp the time;
attempts schema holds no raw address; prune removes an 8-day-old attempt, keeps a 1-hour-old one, and leaves
signups untouched.

**Two defects found by these tests, both fixed:**

1. `array_length(lists, 1) >= 1` returned NULL for an empty array, so `'{}'` was accepted. Fixed in
   migration `0025` with `cardinality(lists) >= 1`; the test now fails closed.
2. The first concurrency test used a five-row single-statement insert, which Postgres rejects with 21000
   ("ON CONFLICT DO UPDATE command cannot affect row a second time"). That is not the semantics Phase 3
   needs, so the test was rewritten to race two real psql connections.

## Recommended Phase 3

The validated signup server function: a `.strict()` Zod schema reusing `normalizeEmail`/`isValidEmail`,
rate limiting via `NEWSLETTER_HASH_PEPPER` + `newsletter_attempts` (window and limit to be confirmed as a
product decision), the `ON CONFLICT (email)` upsert, generic coded results, and a consent module that
**fails closed** until approved wording exists. The MELT form is wired in the same phase; no provider call.

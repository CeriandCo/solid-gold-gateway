## 2. Phase 2 schema re-audit

Read from `drizzle/migrations/0024_newsletter_signups.sql` and `0025_newsletter_lists_cardinality.sql` and
confirmed against the live database.

- Tables: `public.newsletter_signups`, `public.newsletter_attempts`.
- Signup columns: `id uuid` default `gen_random_uuid()`, `email text`, `lists text[]`, `consent_version text`,
  `consent_text text`, `consented_at timestamptz`, `source text`, `created_at`/`updated_at timestamptz`
  default `now()`. All NOT NULL.
- Constraints: `UNIQUE (email)`; email length 3–254; `email = lower(email) AND email = btrim(email)`;
  `cardinality(lists) >= 1`; `lists <@ ARRAY['daily-note','weekly-brief']`; consent_version 1–80;
  consent_text 1–4000; source 1–200.
- List values: exactly `daily-note` and `weekly-brief`.
- Timestamps: `updated_at` by trigger `newsletter_signups_updated_at`; `consented_at` untouched by it.
- Attempts: `id bigserial`, `ip_hash text`, `created_at timestamptz`. Index `(ip_hash, created_at)`.
- Prune: `newsletter_prune_attempts()` deletes attempts older than 7 days, cron `29 3 * * *`; signups never pruned.
- Access: `GRANT ALL … TO service_role`, RLS enabled, zero policies on both tables.

**Differences from the Phase 1 proposal:** none that affect this phase. The empty-list rule uses
`cardinality`, not `array_length` (the Phase 2 fix). The server code is written against the actual schema.

## 3. Public server-function architecture

```
subscribeToMelt (createServerFn POST, src/lib/newsletter.functions.ts)
  → thin inputValidator: passes raw input through, unvalidated
  → await import("./newsletter/signup.server")   ← server-only, inside the handler
  → runMeltSignup(data)                          ← all checks, then service-role persistence
```

Identical to the commerce precedent (`createGiftCardCheckout` → `runGiftCardCheckout`). One narrowly scoped
operation; no generic privileged database function is exposed.

## 4. Strict input contract

```ts
z.object({
  email:  z.string().min(1).max(1000),
  lists:  z.array(z.enum(["daily-note","weekly-brief"])).min(1).max(2),
  source: z.literal("aurum_melt"),
}).strict()
```

`.strict()` rejects any unknown key outright. Tested rejections include `consentText`, `consent_text`,
`consentVersion`, `consentedAt`, `createdAt`, `updatedAt`, `ipHash`, `ip_hash`, `provider`, `audienceId`,
`status`. None of those can reach persistence.

## 5. Email normalisation and validation

Refuses any address containing a control character (`/[\u0000-\u001f\u007f]/`) rather than stripping it,
because stripping would silently subscribe a different address than the one submitted. Then
`normalizeEmail` from `admin.server.ts` (trim + lowercase), length 3–254, and the repository's existing
`isValidEmail` syntax check. No RFC-5322 parser. The email is never logged.

Tested: ordinary valid; surrounding whitespace; uppercase; malformed; missing `@`; missing domain; internal
whitespace; control character; overlength; empty.

## 6. Preference validation

Allowlisted to the two Phase 2 values via `z.enum`, minimum one selection (mirroring the database
`cardinality >= 1`), duplicates collapsed before the write. Rejected before any privileged call. These are
MELT content preferences, not provider list identifiers — the module comment says so.

## 7. IP trust behaviour

`cf-connecting-ip` only, read with `getRequestHeader`. Cloudflare overwrites it at its own edge.
`x-forwarded-for` and `x-real-ip` are never read — proven by a test that sets a spoofed
`x-forwarded-for` and shows it produces no attempt row under the spoofed identity. When the header is
absent the request falls into one shared bucket and is still rate-limited: it never fails open. Raw IP is
never stored.

## 8. NEWSLETTER_HASH_PEPPER

Read as `process.env["NEWSLETTER_HASH_PEPPER"]` inside `newsletterPeppered()` in a `.server.ts` module, at
request time. Never exposed, returned, logged or persisted. Missing or blank → `null` → the request stops
with a generic `unavailable` before any database write. There is no fallback to an unhashed IP,
`COMMERCE_HASH_PEPPER`, a hard-coded pepper or an empty string — tested explicitly, including with
`COMMERCE_HASH_PEPPER` present.

## 9. Hashing

`SHA-256(pepper + ":" + ipBucket)`, lowercase hex — the same formatting convention as `peppered()`, kept as
a separate narrow implementation so commerce behaviour is untouched. Tested: same IP + same pepper gives the
same 64-hex fingerprint; a different pepper gives a different one; no stored `ip_hash` contains the raw IP.

## 10. Rate-limit constants and why

5 per 15 minutes, 20 per 24 hours. No newsletter limits exist anywhere in the repository or docs — searched
Phase 1/2 material and found only the Phase 1 "proposed default" note. These are therefore labelled in code
as **operational defaults, not a product or client decision**, and are four constants in one server-only
file. Commerce checkout uses 10/15 min and 30/day; a newsletter signup is far less frequent, so these are
deliberately tighter. Nothing is in the database schema.

## 11. Rate-limit ordering

1. trusted IP bucket → 2. require the pepper (fail closed) → 3. insert the attempt → 4. count both windows →
5. stop if over → 6. strict schema validation → 7. email/preference normalisation → 8. consent availability →
9. persist. Malformed requests consume quota (step 3 precedes step 6), so junk traffic is not unlimited. No
provider is called.

## 12. Consent fail-closed design

`src/lib/newsletter/consent.server.ts` holds `APPROVED_CONSENT = null`. `approvedConsent()` returns the
snapshot only when a version (1–80 chars) and text (1–4000 chars) are both present and non-blank.
`runMeltSignup` defaults its consent dependency to `approvedConsent()`, and returns generic `unavailable`
with **zero** persistence while it is null.

There is no environment-variable switch and no default, so a mistyped variable cannot turn persistence on
with unapproved text. No `[CLIENT-APPROVED…]` placeholder exists at runtime. The component's
`2026-09-20` placeholder is not read by the server and is not treated as approved.

## 13. Acknowledgement-contract decision

Audited `src/components/aurum-subscribe-section.tsx`: the form has an inline consent statement and **no
affirmative checkbox**. Therefore the server contract does **not** accept an acknowledgement boolean — the
server would be pretending the browser confirmed something it never asked. The consent snapshot is entirely
server-owned and is recorded on the strength of the wording displayed.

If the client chooses a checkbox UX, Phase 4 adds `acknowledged: z.literal(true)` plus a literal version
token, exactly as commerce C-9 does. The contract is small enough that this is an additive change.

## 14. Source allowlist

`z.literal("aurum_melt")` — one canonical value, stored verbatim. The database permits 200 characters, but
the browser can send only this. No referrer, UTM, gclid or `ref` value is accepted or persisted; marketing
attribution is deliberately outside the security contract.

## 15. Public result contract

`{ ok: true }` on success; `{ ok: false, code: "invalid_request" | "rate_limited" | "unavailable" }`
otherwise. A test asserts the success object's keys are exactly `["ok"]`. No provider codes exist, no
internal detail, no count, no row id.

## 16. Duplicate privacy behaviour

A first signup and a repeat signup return the identical object; the test compares them directly. Nothing
distinguishes created from updated, and no existing lists, consent history or id is returned.

## 17. Upsert behaviour

`supabaseAdmin.from("newsletter_signups").upsert({...}, { onConflict: "email" })`. The payload carries only
email, lists, server consent version/text, server `consented_at` and the fixed source, so `id` and
`created_at` are outside the conflict update and are preserved; `updated_at` is moved by the database
trigger. Proven: after a repeat with different preferences and a different consent version, `id` and
`created_at` are byte-identical while lists, consent version, consent text and `consented_at` all refresh.
Request data never sets a system timestamp.

## 18. Concurrency

Two `runMeltSignup` calls for the same address issued together both return `{ ok: true }` and leave exactly
one row. There is no application-level check-then-insert anywhere in the path; the unique constraint plus
`ON CONFLICT` is the only arbiter.

## 19. Logging and privacy

One helper emits `[newsletter] signup refused: <reason>` with fixed reasons: `pepper missing`,
`rate limited`, `invalid payload`, `invalid email`, `consent configuration missing`,
`persistence failed (<sqlstate>)`. Plus one line when `cf-connecting-ip` is absent. A test captures all
console output during a real run and asserts it contains neither the raw IP, nor the email, nor the pepper.
The IP hash, consent text and full payload are never logged.

## 20. Service-role boundary

`supabaseAdmin` is imported only in `signup.server.ts`. `newsletter.functions.ts` loads that module with
`await import()` inside the handler. `newsletter/types.ts` is the only client-safe module and contains no
server code. Production build scan of `dist/client` for `NEWSLETTER_HASH_PEPPER`, `newsletter_signups`,
`newsletter_attempts` and `runMeltSignup`: **zero matches**.

## 22. Test-only consent injection

`runMeltSignup(data, deps)` takes `deps.consent`, defaulting to `approvedConsent()`. Tests pass

## 34. Deviations / blockers

- No acknowledgement boolean in the contract, because the current UI has no checkbox (section 13).
- A control character in the address is rejected rather than stripped — strictly safer than the webhook
  precedent, and the rationale is in the code comment.
- Rate-limit numbers are labelled operational defaults; no repository evidence of client limits exists.
- `NEWSLETTER_HASH_PEPPER` was generated so the boundary is operable; it is infrastructure, not a client
  decision or a provider key.

## 35. Recommendation for Phase 4

Wire the existing MELT form to `subscribeToMelt`: remove the `console.info` stub and fake delay, map the two
checkboxes to `lists`, send the fixed `source`, and render the three coded results as generic messages
(success identical for new and existing addresses, a plain "too many attempts" for `rate_limited`, and a
plain "not available right now" for `unavailable`, which is what production will return until the consent
wording is approved). Keep the existing labels, `aria-describedby` and `aria-live` region. Add the approved
consent copy to `consent.server.ts` in the same change only if the client has supplied it by then; otherwise
the form ships knowingly returning the unavailable state, and the copy switch is a one-line later edit.
